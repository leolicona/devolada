# Bug Fix: the Links roster stops at the first 1,000 customers, so the rest have no payment link

- **Slug**: links-roster-cap
- **Fixed**: 2026-09-19
- **Assessment**: ./assessment.md
- **Status**: applied

## Summary

The customer list joins the background read the invoice cap built: the sweep
now runs one kind of pass per list (`pending`, `roster`), and a tenant whose
roster does not fit the ten-page live read is served the sweep's last
finished pass — every customer, each with a link, `complete: true`, `readAt`
= the pass's end. The roster sweep creates each page's links as it stores it,
so the first open of Links on a 6,509-customer tenant is a read. A tenant
that fits keeps reading live, unchanged. The decision left open in the
assessment (rest or refresh continuously on a large tenant) was taken as
recommended there: continuous, like the invoices, a constant either way.

## Diff Highlights

One sweep, two kinds (`snapshot.ts`):

```ts
const KINDS: Record<SweepKind, KindSpec> = {
  pending: { kind: "pending", livePages: PENDING_LIVE_PAGES,
    firstPath: (w, now) => w.pendingInvoicesPath(now),
    page: async (w, path) => { const { invoices, next } = await w.pendingInvoicesPage(path); return { rows: invoices, next }; } },
  roster:  { kind: "roster", livePages: ROSTER_LIVE_PAGES,
    firstPath: (w) => w.customersPath(),
    page: async (w, path) => { const { customers, next } = await w.customersPage(path); return { rows: customers, next }; },
    /* the links are created where the list is read */
    onPage: async (db, businessId, rows) => { await ensureLinks(db, businessId, rows as WispHubCustomer[]); } },
};
```

The roster's door, decided by data like the invoices':

```ts
export async function readRoster(db, businessId, wisphub, now, opts = {}) {
  const row = await sweepRowOf(db, businessId, "roster");
  if (row && servesSnapshot(row, wisphub)) { … return { customers, complete, source: "snapshot", readAt }; }
  const live = opts.display ? await rosterForDisplay(businessId, wisphub, now)
                            : { ...(await wisphub.listCustomersFull()), readAt: now.getTime() };
  if (!live.complete) await wakeSweep(db, businessId, "roster", wisphub.baseUrl, now);
  return { ...live, source: "live" };
}
```

The page's side effect runs after the cursor moved, so a failure there costs
one tick and never the page:

```ts
if (spec.onPage) {
  try { await spec.onPage(db, row.businessId, rows); }
  catch (e) { console.warn(`${row.kind} sweep: page side effect failed …`); }
}
```

## Deviations from Assessment

- **The paged door reads live, not through the cache.** The assessment
  routed `listLinks` through the same read as the roster; the first cut
  did so through the 30-second display cache, and US-D07 D5's recycled-id
  scenario failed: that door had always read WispHub fresh (`listCustomers`
  was uncached), and the test pins that it sees a changed usuario at once.
  `readRoster` got the same `display` switch `readPendingInvoices` has —
  the roster keeps its cache, the paged door reads the adapter directly —
  and the existing suite passed untouched.
- **Branch base.** This worktree's branch sat on `7c30a8e`, a duplicate of
  what `main` holds since #219's squash (`a14aada`). A hard reset was
  refused by the permission classifier, so the fix lives on a new branch
  `claude/links-roster-cap` cut from `origin/main`; the old branch
  `claude/modest-austin-6cbb4d` is untouched and can be deleted.
- Nothing else departed from the assessment.

## Follow-ups

- **`main` carried #217's `wisphubFailure(c, e, "panel")` audience**: the
  roster's failure mapping is unchanged by this fix and the sweep's
  `WISPHUB_AUTH_FAILED` rests the row for `REST_MS`, as before.

  snapshot; both passes rebuild in minutes, during which the payer's page
  answers *"no pudimos consultar tu cuenta"* for customers beyond page five
  and Links/Cobros show their banners. Not on the ISP's billing morning.
- **WispHub call volume**: two continuous passes on a large tenant, ~20
  calls a minute. If WispHub pushes back, the roster kind's rest is one
  constant (`KINDS.roster` could carry its own `REST_MS`).

  stored directory to read — `wisphub_pages` of kind `roster`, one JSON page
  per 100 customers. A derived `customers` table indexed for search is that
  spec's call, not this fix's.
