# Bug Fix: a customer beyond the first 500 pending invoices is told they owe nothing — or asked the plan's price

- **Slug**: pending-invoice-cap
- **Fixed**: 2026-09-19
- **Assessment**: ./assessment.md
- **Status**: applied

## Summary

The debt question is no longer answered by a five-page read that silently
stops. A tenant whose pending list fits that read is read live, as before; a
tenant whose list does not is read by the every-minute sweep, a few pages per
tick, and every path — the payer's page, the submission, the verdict, the
provisional release, Cobros — serves the last finished pass. A zero from a
cut-off list now answers "cannot confirm" (`WISPHUB_READ_INCOMPLETE`, which the
payer's page already renders as *"No pudimos consultar tu cuenta en este
momento"*), never the green "al corriente" and never the plan's price; and an
invoice id that came from the snapshot is re-read fresh before money is
registered against it.

Two product decisions from the assessment's Open Questions were taken as
recommended there, since the creator asked to continue: the neutral page state
while the list is unconfirmed (no new copy — the page's existing outage state
says exactly the right thing), and the snapshot's age as the cost of a correct
amount (a full pass every ~7 minutes at this ISP's size).

## Diff Highlights

The read rule, decided by data (`pending-snapshot.ts`):

```ts
/* A finished pass longer than the live budget, read from the address
   the tenant is on today. A shorter one means the live read is complete
   on its own, and fresher. */
function servesSnapshot(row, wisphub) {
  return row.baseUrl === wisphub.baseUrl && row.servedPassId !== null
    && (row.servedPages ?? 0) > PENDING_LIVE_PAGES;
}
…
/* A cut-off read is the signal the sweep exists for */
if (!live.complete) await wakePendingSweep(db, businessId, wisphub.baseUrl, now);
```

When a zero can be believed (`debt.ts`):

```ts
export function nothingOwedIsProven(customer, pending): boolean {
  if (customer.carriedBalanceCents < 0) return true;   // a credit: the record is never truncated
  if (customer.billingStatus === "paid") return true;   // WispHub's own label
  if (!pending.complete) return false;                  // a cut-off list proves nothing
  return pending.source === "live" || customer.billingStatus !== "due";
}
```

The verdict, before money moves (`validation.ts`):

```ts
const ispDebtCents = debt.totalCents;           // was: || customer.planPriceCents
let invoiceId = debt.invoiceId;
if (pending.source === "snapshot" && invoiceId !== null && customer) {
  invoiceId = await stillPendingInvoiceId(wisphub, customer.usuario, pending);
}
```

The sweep's swap — a pass is served only once it is finished, a tenant that
fit the live budget goes back to resting, one that did not is read again at
once:

```ts
await patch({ servedPassId: state.livePassId, servedPages: state.livePages, …,
  restUntil: state.livePages > PENDING_LIVE_PAGES ? null : new Date(now + REST_MS) });
```

## Tests Added or Updated

`apps/api/test/pending-invoice-cap.test.ts` (WispHub fetch-mocked at its
origin, seven pages of 100 with the customer's invoice on the last one, the
sweep driven by hand):

- *a cut-off read is never "owes nothing"*
  - the payer's page answers 503 `WISPHUB_READ_INCOMPLETE`, not `no_debt`, and
    the cut-off read creates the sweep row
  - the submission answers 503 — no plan price, no payment row
  - a live read that fits stays live and complete; no sweep row is born
- *the sweep reads the tenant whole and every path serves it*
  - the page shows the real 350.00 from page seven; Cobros lists all 700 with
    `complete: true` and `readAt` = the pass's end
  - the verdict settles `confirmed`/`exact` against 350.00 and registers on
    the real `id_factura` after the fresh detail read; no `POST /facturas/`
  - an invoice paid meanwhile (detail says "Pagada") yields to the customer's
    next one
  - a customer the finished pass does not list: a live "due" label answers
    503, a "Pagadas" label answers `no_debt`
  - what Devolada registered is gone from the page and from Cobros before the
    next pass
- *the sweep itself*
  - a 500 mid-tick keeps the cursor (`offset=300`), the next tick resumes and
    finishes with all seven pages stored
  - a tick reads at most `SWEEP_PAGES` and continues next minute
  - a tenant that fits rests `REST_MS`, the next tick reads nothing, and its
    page still asks WispHub live
  - a disconnected tenant rests with `WISPHUB_NOT_CONFIGURED` instead of
    failing every minute

No existing test changed: the live path is byte-for-byte what it was for the
tenants the suite describes.

## Deviations from Assessment

- **Scope expansion that `main` had already made.** `routes/payment-requests/handler.ts`
  chunked the Cobros `IN (…)` at `D1_MAX_PARAMS - 1`, leaving room for the
  business id but not for `source = 'panel'` — 99 usuarios + 2 = 101 bound
  parameters, and D1 refuses at 100. The bug's 700-invoice fixture is the
  first read in this suite to list 99 debtors at once, so it surfaced here and
  was fixed in place. The same defect was found and fixed independently on
  `main` the same day as bug `cobros-links-lookup-params` (#218), with a
  suite-wide guard in `test/setup.ts` that now counts every bound parameter;
  on merge that version, and its comment, won. The finding stands: Cobros
  answered 500 for any ISP with 99 or more customers on the pending list.
- **The neutral page state uses an existing door.** The assessment weighed a
  new `status` value. The page's outage branch (`link.isError` → *"No pudimos
  consultar tu cuenta en este momento. Intenta de nuevo en unos minutos."*)
  already says the right thing, so the API answers 503 with a new, honest code
  and the contract is unchanged. The submission's fallback copy (*"No pudimos
  recibir tu comprobante. Intenta de nuevo en unos minutos."*) covers the
  stale-page case the same way.
- **The fresh invoice check lives in the verdict, not in `attemptReconnection`.**
  It is only needed when the id came from a snapshot; putting it in the
  adapter would have added a call to every registration, including the retry
  path and the small tenants whose live read is seconds old, for no product
  reason — and every registration test with it.
- **Reads split by measured size, not by a single mode.** The assessment
  described "every debt path reads the snapshot". Tenants that fit the live
  budget keep reading live (fresher, and exactly today's behaviour), and the
  sweep engages only from a cut-off read. Same fix for the ISP that has the
  bug; no cost, no staleness and no behaviour change for the ones that do not.
- **Cheapest-thing-first not tried.** The customer-filter probe (one curl per
  parameter name) was offered and not taken; the fix assumes the adapter's
  2026-08-16 finding stands.

## Follow-ups

- **Verify `GET /facturas/<id>/` once, with the ISP's key** (one HTTPS read to
  WispHub, nothing else): `invoiceState()` reads `estado` as `1`/"Pendiente"
  for pending and `2`/`3`/"Pagada"/"Cancelada" for closed, and treats any other
  shape — or a route WispHub does not serve — as "cannot tell, proceed as
  before". So the guard degrades to today's behaviour if the guess is wrong,
  never worse; but it only protects if the guess is right.
- **Measure the ISP's real pending count and list order** (the assessment's
  first open question) to size `SWEEP_PAGES`/pass time against reality; the
  constants are exported, not env knobs, on purpose.
- **The `/links` roster** (1,000-customer cap, same mechanism) should ride this
  sweep: a second pass kind over `/clientes/` with the same row/pages shape.
  Feature spec, not a bug.
- **Decisions to amend in their home documents**: provider-latency D3 and
  debt-truth D4 are amended in the code comments (`cache.ts`, `client.ts`,
  `debt.ts`); the archive specs are read-only, so the amendment lives with the
  code, as the repo's rule says.
