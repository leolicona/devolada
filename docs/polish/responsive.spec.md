# Spec: Responsive, measured in a browser

`TESTING.md` layer 4 was reserved for the questions a simulated DOM cannot answer, and rule 6 says so outright: assertions about real colour and layout belong here. This spec builds that layer and uses it for the responsive pass — then lets it check the two things the earlier passes had to leave open, real contrast and touch-target size.

## Decisions

- **D1 — Static previews, not the full stack.** Both apps are served as built bundles and the API is stubbed with Playwright route interception. For geometry the backend is irrelevant, and a preview starts in seconds where `wrangler dev` + D1 + the IdP take minutes. The stubs mirror the real contracts, same discipline as MSW.
- **D2 — Stubs never answer a navigation.** The apps are served from the origin they call, so a glob for `/cashbox` matches both the API request and the browser opening the `/cashbox` page. Fulfilling the navigation hands the browser JSON and the screen never renders — the first run "failed" for that reason alone. Document requests now always pass through.
- **D3 — The failure message is the finding.** `expectNoHorizontalScroll` reports the actual widths, `expectTouchTargets` names the offending control and its height. A red build that only says `expected true` sends the next person back to the browser to re-derive what was already known.
- **D4 — Run on deploy-dev, not per PR.** `CICD.md` D3 decided E2E belongs after the merge, not in the iteration loop; nothing here changes that trade. The suite is one command (`pnpm e2e`) for local use.
- **D5 — 44px, not 48px, is the assertion.** `FRONTEND.md` asks for ≥48px touch targets and 64px on the charge path; the automated floor is set at 44px (the WCAG/Apple minimum) so that a deliberate 46px chip is a design decision rather than a build failure, while a 17px tap target is caught.

## What it found

- **The store PWA's primary links were 17px tall.** `<Link>` wrapping `<Button>` leaves an inline `<a>`: the button looked 48px, the anchor the browser hands the finger was 17px. Five of them, in both apps.
- **Entregas scrolled sideways at 360px** — 416px of content in a 360px screen. A `w-full` child inside a wrapping flex row grows its own container; the actions are stacked now.
- **The charge feed hid the customer name on a phone.** Time, badge, amount and chevron squeezed the flexible name column to zero, so the feed showed an amount without saying who paid it. The row becomes a card below `sm`.
- **`--color-text-tertiary` was carrying information.** The token is documented as "placeholder, disabled" — both exempt from the contrast rule — but the screens used it for the folio, the customer's zone, ledger times and settings hints, at 2.4–2.5:1 in light and 3.0–3.3:1 in dark. The token is unchanged; the fifteen informational uses now take the readable tone. Placeholders and decorative icons keep it.

That last one is the layer earning its keep: `contrast-lint` measures the pairs someone thought to list, and nobody had listed the placeholder colour as body text.

## Contract

`pnpm e2e` — Playwright, chromium, two static previews (4173 store PWA, 4174 admin).

- `tests/e2e/responsive.spec.ts` — 360px phone floor, 768 tablet, 1280 desktop
- `tests/e2e/contrast.spec.ts` — axe with `color-contrast` and `target-size` only, each screen in light **and** dark (`emulateMedia`); the markup rules stay in the component layer where they run per PR

## Scenarios

1. No screen scrolls sideways at 360px, in either app (US-P03, D1)
2. Every visible control clears 44px, and the decisive charge action is full-width and ≥48px (US-P03, D5)
3. The admin's sidebar becomes a bottom bar below `lg` and returns on desktop (US-P03)
4. Confirming a handover is reachable on a phone and still takes two taps (US-P03, cash-drops D6)
5. Both apps pass axe's contrast and target-size rules in light and dark (US-P02, US-P04)
